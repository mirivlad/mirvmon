# Roadmap MirvMon

Этот roadmap фиксирует текущее направление развития MirvMon после выпуска
`v0.7.3`. Стабильный релиз на момент обновления документа — `v0.7.3`.
История уже выпущенных изменений сохраняется в [CHANGELOG.md](CHANGELOG.md) и
[docs/releases](docs/releases).

## Текущее состояние: v0.7.3

MirvMon уже закрывает два основных сценария эксплуатации:

- мониторинг серверов через native Go agent с исходящими HTTPS-запросами;
- централизованный мониторинг HTTP(S)-сайтов без отдельного агента.

Система хранит историю в TimescaleDB, ведёт инциденты и maintenance windows,
отправляет Telegram/SMTP-уведомления через outbox, поддерживает audit log,
самодиагностику MirvMon и удалённое обновление native agents.
Начиная с v0.7.0 MirvMon также ведёт отдельные проактивные наблюдения: выявляет
устойчивые отклонения CPU/RAM от собственной исторической нормы сервера и
прогнозирует риск заполнения дисков до обычного порогового инцидента.

## v0.5.3 — Массовое обновление агентов (выпущен)

Цель: убрать ручное протыкивание обновления на каждом сервере, не создавая второй
системы rollout/campaigns.

На странице серверов появляется действие **«Обновить все устаревшие»**. Оно
повторно использует тот же application/domain service и те же проверки, что
одиночное обновление агента.

- команда создаётся только для устаревших и совместимых `self_update_v1` agents;
- уже обновляющиеся, актуальные или неподдерживаемые агенты безопасно пропускаются;
- перед запуском UI показывает количество подходящих агентов и целевую версию;
- результат операции показывает, сколько обновлений запланировано, уже выполняется
  и сколько агентов нельзя обновить автоматически;
- агенты получают обычные индивидуальные update commands через существующий
  outbound config poll; отдельный fleet worker не вводится.

## v0.5.4 — Обзор парка агентов (выпущен)

Цель: сделать уже существующие сведения об агентах удобными для эксплуатации
всего парка без изменения protocol ради одного dashboard.

- количество актуальных и устаревших версий;
- текущие update states и неуспешные обновления;
- понятные operator-facing transport/runtime состояния агента;
- заметная диагностика накопившейся локальной очереди и проблем доставки, когда
  агент уже сообщает достаточные данные для этого;
- быстрый переход к серверам, требующим ручного вмешательства;
- operator-facing текущее состояние на основных operational-экранах обновляется
  без ручного reload: server/site/group state, active incidents, notification
  queue и системная диагностика используют visibility-aware web polling;
- server metrics также обновляются автоматически, сохраняя выбранный period/custom
  range и пользовательский zoom/pan viewport по временным координатам.

Реализация использует существующие agent metadata, last contact, server health и
update state. Локальная retry-очередь не показывается числом, потому что текущий
protocol не сообщает её глубину; новый protocol ради одного dashboard не вводится.

## v0.5.4.2 — Live-metrics redraw hotfix (выпущен)

Исправлена перерисовка сохранённого zoom/pan после автоматического обновления
метрик: viewport восстанавливается и отображается сразу, без дополнительного
клика или движения мыши по графику.

## v0.5.4.3 — Live zoom follow hotfix (выпущен)

Wheel/pinch zoom больше не превращает live-график в фиксированный исторический
срез: масштаб сохраняется относительно свежего края series, поэтому новые точки
продолжают появляться после автоматического обновления. Pan и drag-zoom оставляют
абсолютный исторический диапазон зафиксированным до `Reset zoom`. Общий live-refresh
также больше не блокируется обычным focus кнопки, ссылки или canvas.

## v0.5.4.4 — Live zoom scrolling hotfix (выпущен)

Любой zoom/pan графика теперь сохраняет свой масштаб, но при каждом live-refresh
сдвигается на ту же временную величину, на которую сдвинулся правый край series.
Это убирает эффект «замороженного» графика после zoom без сброса выбранного масштаба.

## v0.5.4.5 — Middle-mouse timeline pan (выпущен)

На графиках серверных метрик средняя кнопка мыши теперь позволяет перетаскивать
видимый временной диапазон влево и вправо. Wheel zoom и live-scroll сохраняются;
во время активного перетаскивания live-refresh не заменяет canvas.

## v0.6.0 — Backup & Disaster Recovery (выпущен)

Цель: сделать восстановление MirvMon после потери installation host штатной
операцией из web UI.

Основной сценарий восстановления:

1. развернуть новый чистый Compose stack;
2. пройти `/setup` и войти временным администратором;
3. открыть системные настройки резервного копирования;
4. загрузить backup-файл и пройти его предварительную проверку;
5. запустить восстановление и после завершения войти учётной записью из backup.

Требования:

- backup имеет собственный версионированный формат и manifest/checksums;
- полный backup защищается отдельным паролем резервной копии;
- восстановление допускается на stack с новым `APP_KEY`;
- зашифрованные application secrets при restore расшифровываются старым
  backup-контекстом и заново шифруются текущим `APP_KEY`;
- permanent agent credentials и server identity сохраняются так, чтобы уже
  установленные агенты продолжили работу без переустановки и ротации токенов;
- до изменения БД проверяются формат backup, совместимость версии и целостность;
- при восстановлении более старой поддерживаемой схемы после импорта применяются
  обычные forward migrations;
- на время restore ingestion и фоновые workers переводятся в контролируемое
  maintenance-состояние;
- после restore выполняются integrity checks, текущая временная admin session
  завершается, а пользователь входит данными из восстановленной БД;
- отдельный integration test воспроизводит disaster recovery между установками с
  разными `APP_KEY` и подтверждает успешный metrics push от существующего агента.

История метрик входит в полный disaster-recovery backup. Облегчённый
configuration-only backup остаётся возможным будущим расширением.

## v0.6.1 — Backup job visibility hotfix (выпущен)

Исправлен операторский UX асинхронных backup: после ухода со страницы и повторного
входа MirvMon снова показывает persistent backup jobs из `/app/var/dr`, включая
очередь/выполнение, завершённые и неуспешные операции. Для готового архива видны
имя, размер, время создания/завершения, точное время автоудаления и кнопка
скачивания. Готовые временные архивы по-прежнему физически удаляются DR worker
через 24 часа после завершения; новые миграции и изменения agent protocol не
требуются.

## v0.6.2–v0.6.9 — эксплуатационная стабилизация (выпущены)

После DR-релиза MirvMon получил защиту от ложных offline-событий при потере
внешней связности самого MirvMon, настраиваемый connectivity quorum, явную
трёхуровневую модель `user` / `operator` / `admin`, усиление безопасности
Windows installer enrollment и централизованный `RolePolicy`. Детали выпущенных
изменений находятся в [CHANGELOG.md](CHANGELOG.md) и [docs/releases](docs/releases).

## v0.7.0 — Проактивные наблюдения (выпущен)

Цель: научить MirvMon замечать эксплуатационно значимые изменения **до**
срабатывания обычного порогового алерта. Это не новый вид инцидента: наблюдение
означает «формально всё ещё допустимо, но поведение сервера стало необычным или
текущий тренд скоро потребует вмешательства».

### Пользовательская модель

В UI появляется отдельный раздел **«Наблюдения»**. Он не смешивается с
`Incidents / Events` и имеет собственный жизненный цикл.

Первая версия поддерживает два класса наблюдений:

1. **Аномалия поведения** — метрика заметно и устойчиво ушла от собственной
   исторической нормы сервера, оставаясь ниже warning threshold. Например, DB1
   обычно держит CPU 2–3%, но несколько десятков минут работает на 18–23%, либо
   такие отклонения повторяются сериями.
2. **Прогноз обслуживания** — устойчивый тренд показывает, что скоро потребуется
   действие. Первый обязательный сценарий — рост заполнения диска с прогнозом
   достижения warning threshold и/или фактического заполнения.

Наблюдение обязано объяснять себя: сервер, метрика/диск, текущий уровень,
историческая норма, длительность/повторяемость, прогнозируемое время события и
оценка уверенности, когда она применима. «Чёрный ящик сказал, что тут странно»
не считается приемлемым UX.

### Базовая модель нормы

- baseline строится отдельно для каждой пары `server + metric`;
- для CPU/RAM используются устойчивые статистики исторических hourly aggregates,
  а решение принимается по свежим 5-минутным окнам raw metrics;
- после установки нового сервера действует период обучения: наблюдение уровня не
  создаётся, пока нет минимум нескольких суток истории;
- одиночный короткий spike не считается аномалией: требуется устойчивое
  отклонение или несколько отделённых друг от друга отклонений за окно анализа;
- детектор не дублирует обычный alert: если значение уже достигло warning
  threshold, дальнейшая ответственность остаётся у incident/alert pipeline;
- v0.7.0 использует детерминированную статистику, а не ML/LLM. Алгоритм должен
  быть воспроизводимым тестами и объяснимым оператору.

### Прогноз заполнения диска

- анализируется отдельная история каждого `disk_used_*`;
- недавняя явная очистка/освобождение места начинает новый сегмент тренда, чтобы
  старый saw-tooth цикл не искажал текущий прогноз;
- прогноз строится только при достаточной длительности данных, положительном
  темпе заполнения и приемлемом качестве линейного тренда;
- наблюдение создаётся заранее, пока диск ещё ниже warning threshold;
- в деталях хранятся темп роста, качество тренда, прогноз warning threshold и
  прогноз 100% там, где их можно разумно оценить.

### Дедупликация и жизненный цикл

Каждый детектор выдаёт устойчивый fingerprint. Продолжающееся событие обновляет
одно наблюдение вместо генерации новых строк и новых уведомлений.

Для аномалии:

`detected -> active -> resolved`

Оператор может выбрать **«Считать это нормальным»**. Тогда fingerprint сохраняется
как принятый паттерн (`accepted_normal`), и сходное поведение больше не создаёт
уведомления. Принятое решение видно в UI и может быть отменено; скрытой
необратимой «магии обучения» быть не должно.

Для прогнозного наблюдения:

`detected -> active -> handled -> resolved -> detected again`

Кнопка/галочка **«Обработано»** снимает текущую задачу. Пока тот же прогноз
остаётся активным, MirvMon не напоминает повторно. После фактического исчезновения
условия наблюдение переходит в resolved и снова вооружается: следующий независимый
цикл заполнения диска может создать новое уведомление.

Если причина исчезла без нажатия оператором, активное наблюдение закрывается
автоматически. Отсутствие данных само по себе не считается исчезновением:
auto-resolve разрешён только после реальной оценки той же `server + metric` пары;
maintenance, DR pause и observation gap не должны rearm-ить обработанный прогноз.

### Уведомления

- отправляется одно уведомление на новый fingerprint аномалии;
- новый цикл прогнозного наблюдения может уведомить снова только после того, как
  предыдущий цикл действительно завершился;
- используются уже настроенные для данного сервера Telegram/e-mail recipients с
  существующим fallback на общие настройки;
- observation notification имеет собственный event type и ссылку на отдельный
  раздел наблюдений, а не маскируется под warning alert;
- maintenance и DR coordination не должны порождать ложные наблюдения или
  notification storms.

### Архитектурные требования

- agent protocol в v0.7.0 не меняется: анализ выполняется по уже сохранённой
  истории TimescaleDB;
- production Compose остаётся двухконтейнерным (`app` + `db`);
- анализ выполняет отдельный supervised `observation-worker` внутри `app`;
- worker пишет heartbeat и отображается в System / MirvMon diagnostics;
- данные наблюдений хранятся отдельно от `alerts`; incident queries и история
  доступности не расширяются observation-строками;
- существующий notification outbox переиспользуется, но observation job не обязан
  иметь `alert_id`;
- detector и state transition logic должны иметь unit tests, repository/state
  machine — integration tests, UI/actions — functional/contract coverage.

### Обязательный объём v0.7.0

- уровень CPU: sustained/recurrent upward level shift относительно baseline;
- уровень RAM: sustained/recurrent upward level shift относительно baseline;
- прогноз роста `disk_used_*`;
- отдельные active/history/accepted-normal представления;
- operator actions «Считать нормальным», «Обработано» и возврат принятого паттерна
  в анализ;
- auto-resolve исчезнувших условий;
- deduplicated Telegram/SMTP delivery через текущих server recipients;
- системная диагностика observation-worker;
- документация алгоритмов, ограничений и периода обучения.

### Не входит в v0.7.0

- нейросетевой/LLM-анализ;
- автоматическое изменение обычных warning/critical thresholds;
- процессная диагностика причины («виноват postgres»): process snapshots могут
  использоваться позже как поясняющий контекст, но не как detector v0.7.0;
- универсальный язык правил и пользовательский конструктор anomaly detectors;
- прогноз CPU/RAM «через N дней»;
- cross-server correlation и поиск общей причины по нескольким узлам;
- автоматические remediation actions.

### План реализации

1. Схема `observations`, state machine и устойчивые fingerprints.
2. Чистый статистический analyzer с unit fixtures для normal/spike/sustained/
   recurrent/accepted-pattern и disk trend/reset cases.
3. Bulk read-model истории TimescaleDB и `observation-worker` с heartbeat/DR lock.
4. Persistence lifecycle: create/update/auto-resolve/handled/rearm/accepted-normal.
5. Observation delivery через существующий outbox и formatter.
6. Отдельный UI `/observations`, operator actions и восстановление принятого
   паттерна в анализ.
7. Интеграционные, functional, contract и performance проверки; обновление
   README/ARCHITECTURE/TECHNICAL_SPECIFICATION/CHANGELOG/release notes.

## v0.7.1 — Дедупликация disk forecast aliases (выпущен)

Hotfix после первого production deployment v0.7.0: один и тот же filesystem мог
появляться как несколько `disk_used_*` метрик для bind-mount/mount aliases и
создавать несколько идентичных прогнозных наблюдений.

- disk aliases определяются сервером без изменения agent protocol: должны совпасть
  текущий usage, reported filesystem size и достаточный участок hourly history;
- при совпадении canonical метрикой становится `disk_used_root`, если она есть;
- для canonical forecast используется самый ранний (минимальный) warning threshold
  из эквивалентных метрик;
- уже существующие active/handled duplicate observations закрываются сразу, без
  ожидания обычного recovery grace;
- canonical fingerprint сохраняется, поэтому hotfix не создаёт повторное
  уведомление по уже присланному root-прогнозу.

## v0.7.2 — Episode semantics и прямые notification links (выпущен)

Hotfix по результатам первых production anomalies v0.7.0–v0.7.1.

- один непрерывный CPU/RAM anomaly episode определяется текущей open observation
  `server + metric + detector`, а не изменяющимся 5-процентным band fingerprint;
- переход нагрузки между `b30`, `b40`, `b45` обновляет evidence одной observation
  и не создаёт повторные Telegram/SMTP notifications;
- после настоящего recovery следующий независимый anomaly episode создаётся заново
  и снова может уведомить;
- действие **«Проверено»** переводит текущий anomaly episode в `handled`, не обучая
  MirvMon считать паттерн нормальным; **«Считать это нормальным»** остаётся
  отдельным явным и обратимым suppression;
- migration 025 схлопывает уже открытые band-дубликаты, сохраняя самый свежий;
- formatter добавляет все применимые internal links: для observation — прямую
  ссылку на server detail и на observation, для server alerts/warnings/recovery —
  прямую ссылку на server detail при настроенном `PUBLIC_BASE_URL`.

## v0.7.3 — Контекстная норма CPU/RAM и hysteresis recovery (выпущен)

Production-наблюдения показали, что одна медиана CPU/RAM за все часы недели не
описывает боевые серверы: низкая ночная нагрузка могла сделать обычные дневные
25–70% «аномалией», а краткое исчезновение trigger преждевременно закрывало
episode.

- `level_shift_v2` использует до 56 дней hourly history и `APP_TIMEZONE`;
- приоритет baseline: тот же weekday + час ±1, затем weekday/weekend + час ±1,
  затем тот же час суток; одной глобальной медианы недостаточно для anomaly;
- при недостаточной contextual history detector не уведомляет и продолжает
  накапливать профиль;
- отсутствие trigger означает `elevated`, а не recovery; попадание в обычный
  warning threshold означает `incident_owned` и тоже не закрывает observation;
- recovery подтверждается только двенадцатью последовательными 5-minute buckets
  ниже recovery boundary, зафиксированной при открытии episode;
- **«Считать это нормальным»** для v2 сохраняет контекст дня/часа и допустимый
  диапазон, поэтому подтверждённый субботний backup не подавляет такой же CPU в
  другой день;
- UI и notifications показывают ожидаемый диапазон текущего контекста, его
  median и глубину истории;
- migration 026 закрывает оставшиеся open v1 episodes; agent protocol не меняется.

## Не входит в v0.5.3–v0.6.0

Следующие направления сознательно не включаются без конкретной эксплуатационной
потребности:

- generic TCP checks;
- ICMP/ping monitoring;
- отдельный DNS monitoring;
- distributed/internal probes через native agents;
- SNMP, topology maps и универсальный конструктор probes;
- rollout waves, update campaigns и иная тяжёлая оркестрация парка агентов.

HTTP(S)-мониторинг остаётся центральной synthetic-проверкой MirvMon. Новые типы
сетевых проверок добавляются только когда они решают практическую задачу, которую
не закрывают уже существующие server agent и website monitoring.

## После v0.6.0

Направления без назначенного релиза:

- более наглядная эксплуатационная статистика: availability, число и длительность
  инцидентов, проблемные объекты и время восстановления;
- простая публичная status page для явно выбранных владельцем объектов;
- облегчённый configuration-only backup, если полный архив окажется слишком
  тяжёлым для регулярного использования;
- дополнительные диагностические возможности агентов по данным реальной
  эксплуатации.

## Принципы roadmap

- MirvMon не должен превращаться в маленький Zabbix только ради количества probes.
- Новый функционал должен закрывать конкретный эксплуатационный сценарий.
- Простая пользовательская операция может использовать сложный внутренний
  механизм, но эта сложность не должна вытекать в UI.
- Backup считается рабочим только тогда, когда доказано полное восстановление на
  чистом stack, а не только успешный `pg_restore`.
- Массовое обновление является надстройкой над проверенным одиночным update flow,
  а не второй системой обновлений.
- NAT-friendly модель сохраняется: native agents инициируют исходящие соединения,
  MirvMon не требует входящих портов на наблюдаемых серверах.
