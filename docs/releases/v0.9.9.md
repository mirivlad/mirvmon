# MirvMon v0.9.9 — ChimePort as a parallel notification channel

## Changes

- Optional ChimePort notifications join the existing durable outbox, independently of Telegram and email. Existing monitoring triggers, incident grouping, cooldown and deduplication remain unchanged.
- New ChimePort transport supports HTTPS with certificate verification, non-redirecting Bearer requests, stable idempotency keys, distinct channels and `429`/`Retry-After` backoff.
- With `CHIMEPORT_CHANNEL=servers`, all MirvMon alerts and recoveries go to one user channel called **Серверы** (slug `servers`).
- Schema migration `033_chimeport_notifications.sql` safely extends `notification_outbox_channel_check`. Existing events and Telegram/email notification records are preserved.
- Additional unit and integration tests, queue filter, and instructions in `docs/CHIMEPORT.md`.

## Compatibility

- Agent protocol and installed agents are unchanged.
- One new SQL migration, applied by the standard migrator; use the new image after migration to ensure the worker understands ChimePort jobs.
- New environment settings are optional; `CHIMEPORT_ENABLED=0` by default.
- Secrets must remain in a volume-mounted file readable only by the MirvMon service user, not in environment variables or source code.

## Deployment

Pull and redeploy `ghcr.io/mirivlad/mirvmon:0.9.9` (`linux/amd64`, `linux/arm64`) in Portainer with the existing `app_data` and `db_data` volumes intact. Follow `docs/CHIMEPORT.md` for token provisioning and `CHIMEPORT_CHANNEL=servers`. Keep Telegram enabled.
