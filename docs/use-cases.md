# Use cases MirvMon

MirvMon не пытается быть универсальной observability-платформой. Основная
задача — понятный self-hosted мониторинг серверов и сервисов, особенно когда
часть узлов находится за NAT или работает на старых ОС.

## Несколько VPS и домашних серверов за NAT

Типичный набор: VPS с публичным адресом, NAS/mini-PC дома, рабочий сервер за
NAT. На каждом узле работает агент, который сам отправляет метрики по HTTPS.
Входящие firewall rules для агентов не нужны.

Подходит для:

- CPU/RAM/load/disk/network метрик;
- контроля выбранных сервисов;
- offline detection;
- Telegram/SMTP уведомлений;
- единой истории инцидентов.

## Смешанный парк Linux и Windows

Одна установка MirvMon может принимать метрики от современных Linux/Windows и
от legacy Windows x64, включая Server 2008 R2/2012/2012 R2.

Это полезно там, где инфраструктуру нельзя одномоментно обновить, но хочется
одинаковую модель агента, очереди и уведомлений.

## Мониторинг хоста самого MirvMon

MirvMon может наблюдать собственный host тем же агентом, что и остальные
серверы. Это сохраняет границу безопасности: приложение не получает Docker
socket и не становится привилегированным только ради host metrics.

При этом `/livez`, `/readyz`, worker heartbeat и состояние БД отвечают за
здоровье самого приложения, а обычный агент — за здоровье ОС/железа хоста.

## Контроль сайтов из одной установки

В `/sites` администратор добавляет публичный или разрешённый внутренний
endpoint и выбирает проверки HTTP-доступности, содержимого, скорости, TLS и
срока регистрации домена. Все probes выполняет `website-check-worker` в
`app`; агентам не выдаются URL и команды для website checks. Для внутреннего
target администратор должен осознанно принять trusted-admin модель, а попытки
уйти на loopback/private/metadata адрес блокируются.

Dashboard, группы и `/alerts` объединяют серверы и сайты, но сохраняют
раздельные status blocks, endpoint labels и ссылки на события сайта. Окно
maintenance продолжает проверки и создание инцидентов, подавляя только
уведомления; pause останавливает проверки.

## Контроль сервисов и плановые работы

Для сервера выбираются сервисы, состояние которых нужно отслеживать. Перед
плановым restart/maintenance можно открыть окно обслуживания: инциденты
продолжают фиксироваться, но внешняя доставка уведомлений временно подавляется.

## Уведомления разным ответственным

Можно задать общих Telegram/email получателей и переопределить их для
конкретного сервера. Например, инфраструктурные VPS отправляют уведомления
администратору, а сервер приложения — ещё и ответственному за приложение.

## Централизованное обновление native agent

После одноразового перехода на capable native agent администратор может выдать
self-update команду из MirvMon. Обновление остаётся исходящим со стороны агента,
проверяет artifact identity/SHA-256 и сохраняет rollback path.

## Когда MirvMon не лучший выбор

Если нужны distributed tracing, ingest произвольных application logs в больших
объёмах, PromQL-совместимая экосистема или Kubernetes-scale service discovery,
лучше использовать специализированный observability stack. MirvMon ориентирован
на компактный и понятный server monitoring с минимальной инфраструктурой.
