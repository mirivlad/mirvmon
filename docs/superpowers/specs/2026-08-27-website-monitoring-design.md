# Мониторинг веб-сайтов: проектирование production-функции

Дата: 2026-08-27
Статус: согласованный дизайн до начала реализации

## 1. Цель

MirvMon получает отдельный полноценный раздел мониторинга веб-сайтов. Он
должен проверять доступность HTTP(S)-ресурсов, ожидаемый код ответа и содержимое,
измерять скорость ответа, контролировать TLS-сертификаты и срок регистрации
домена, создавать инциденты и отправлять уведомления через существующую
инфраструктуру MirvMon.

Функция проектируется сразу для production-эксплуатации. Частичная поставка
упрощённого MVP не является целевым результатом: внутренне реализация может быть
разбита на этапы, но выпуск допускается только после завершения всего объёма и
обязательной проверки.

## 2. Принятый архитектурный подход

Мониторинг сайтов является отдельной предметной областью, а не разновидностью
сервера и не поводом переписывать серверы и сайты в универсальную абстракцию
«ресурс». Сайты получают собственные модели, репозитории, сервисы, worker и UI,
но переиспользуют общие группы, инциденты, очередь уведомлений, maintenance
windows, аудит, авторизацию и визуальный язык MirvMon.

Проверки выполняются централизованно из контейнера `app`. Production Compose
по-прежнему содержит ровно два сервиса: `app` и `db`. Новый
`website-check-worker` запускается под существующим supervisor рядом с другими
worker-процессами.

Архитектура данных результатов сохраняет источник пробы: сейчас это
`probe_kind=app`, а в будущем могут появиться выбранные агенты и идентификатор
конкретного probe. Агентский протокол, UI выбора агентов и распределённый кворум
в эту функцию не входят.

## 3. Предметная модель

### 3.1. Сайт и endpoint

Логический сайт содержит:

- название и необязательное описание;
- общую группу мониторинга;
- необязательный явно заданный основной регистрационный домен;
- признак включённого или приостановленного мониторинга;
- один или несколько URL endpoint;
- общие политики уведомлений и пороги, которые endpoint может переопределять.

Каждый сайт имеет ровно один основной endpoint. Первый созданный endpoint
становится основным. Перед удалением основного endpoint администратор обязан
назначить другой. Дополнительные endpoint позволяют отдельно проверять, например,
главную страницу, `/login` и `/api/health`, не создавая три независимых сайта.

Endpoint содержит начальный URL, расписание, HTTP-метод, правила redirect,
ожидаемые коды, проверки содержимого, пороги времени ответа, настройки
аутентификации и заголовков, а также опцию self-signed TLS.

HTTP-проверка запускается по умолчанию раз в 60 секунд. Интервал задаётся на
уровне сайта и может быть переопределён для отдельного endpoint в пределах
безопасного диапазона, установленного приложением.

### 3.2. Общие группы

Существующие группы серверов становятся общими группами мониторинга. Новая
миграция переименовывает `server_groups` в `monitoring_groups`, сохраняя строки,
идентификаторы и связи серверов. Сайты получают внешний ключ на ту же таблицу.

Одна группа может содержать серверы, сайты или оба вида объектов. Допустима
группа без серверов, предназначенная только для сайтов. В UI группы серверы и
сайты показываются отдельными блоками, но используют общую сводку проблем.

### 3.3. Основные таблицы

Новые миграции вводят как минимум следующие логические сущности:

- `websites` — идентичность сайта, группа, регистрационный домен, состояние и
  политики сайта;
- `website_endpoints` — URL, основной endpoint, расписание, HTTP/TLS-параметры,
  пороги и зашифрованные секреты;
- `website_content_checks` — CSS-селекторы и проверки текста;
- `website_endpoint_state` — компактное текущее состояние и счётчики
  подтверждения переходов;
- текущие состояния TLS-сертификатов и регистрационных доменов;
- `website_check_samples` — TimescaleDB hypertable с измерениями;
- переходы доступности и история инцидентов.

Существующая модель `alerts` расширяется так, чтобы источник был либо сервером,
либо сайтом, но не обоими одновременно. Это обеспечивается ограничением «ровно
один источник». Для website alert обязателен `website_id`, а `endpoint_id`
необязателен: site-level события TLS/domain обходятся без него, endpoint-события
ссылаются только на endpoint того же сайта. Параллельная подсистема website
alerts не создаётся: список событий, maintenance и notification outbox остаются
едиными.

## 4. Выполнение HTTP-проверки

### 4.1. Планирование и конкурентность

Worker выбирает наступившие задания короткой транзакцией с lease и
`FOR UPDATE SKIP LOCKED`. Сетевой запрос выполняется вне транзакции. Результат,
текущее состояние, переход инцидента и постановка уведомления записываются
транзакционно.

Worker имеет ограниченную конкурентность, общий deadline запроса, предел
redirect и предел читаемого тела. Он обновляет `worker_heartbeats` на каждой
итерации, пересоздаёт PDO runtime после отказов БД и завершает процесс при
неизвестной фатальной ошибке, чтобы supervisor мог его перезапустить.

Ручная команда «Проверить сейчас» ставит асинхронное задание с повышенным
приоритетом. HTTP-запрос не выполняется внутри browser request.

### 4.2. Redirect

По умолчанию redirect разрешены, потому что обычный URL главной страницы часто
отвечает `301`/`302`. Проверка следует цепочке до конечного ответа и сохраняет:

- настроенный начальный URL;
- конечный URL;
- число переходов;
- диагностическую цепочку там, где она нужна.

Максимальная длина цепочки — 10 переходов. Зацикливание, превышение лимита и
переход на неподдерживаемую схему являются отдельными ошибками. При включённых
redirect ожидаемый код и содержимое проверяются на конечном ответе; при
выключенных — на первом.

Полная цепочка сохраняется только для неуспешной, ручной или изменившейся
проверки. Для стабильного успешного результата достаточно конечного URL и числа
переходов.

### 4.3. Доступность, код и содержимое

Разрешены только `GET` и `HEAD`. Проверка содержимого всегда требует `GET`.
Методы с побочными эффектами, включая `POST`, не поддерживаются.

Транспортная доступность означает, что checker успешно прошёл DNS, подключение,
TLS и получил синтаксически корректный HTTP-ответ в пределах deadline. Проверка
ожидаемого кода является отдельной опциональной assertion: когда она включена,
по умолчанию допустим любой код `2xx`. Администратор может задать отдельные коды
и диапазоны, например `200`, `200-204` или `401,403`. Поэтому ответ `503` при
выключенной проверке кода означает «endpoint доступен», а при включённой —
«endpoint доступен, но проверка кода не пройдена».

Поддерживаются две проверки содержимого:

- наличие текста во всей прочитанной части страницы;
- наличие элемента по CSS-селектору с необязательной проверкой текста внутри
  найденного элемента.

Регулярные выражения не поддерживаются. Тело читается потоково до 1 MiB,
используется только во время проверки и никогда не сохраняется.

### 4.4. Deadline и диагностика ошибок

Общий deadline endpoint по умолчанию равен 15 секундам и настраивается в
безопасных пределах. Ошибки классифицируются отдельно:

- DNS resolution;
- connect/refused и другие сетевые ошибки;
- timeout;
- TLS handshake или валидация;
- redirect loop, limit или запрещённая схема;
- неожиданный HTTP-код;
- отсутствие ожидаемого содержимого;
- превышение порога скорости;
- превышение лимита ответа;
- внутренняя ошибка checker.

Диагностика не содержит тела ответа, секретных заголовков или credential.

### 4.5. Измерения скорости

Каждая HTTP(S)-проверка собирает DNS, TCP connect, TLS handshake, TTFB и полное
время ответа с учётом redirect, а также код и время каждого hop. Результат
отдельно хранит транспортную доступность и итог всех включённых assertions,
чтобы неверный код, контент или порог скорости не искажал uptime. В основных
графиках показываются только TTFB и полное время; стадии и hop доступны в
диагностике результата.

Для endpoint можно включить warning и critical пороги полного времени ответа.
По умолчанию они выключены. Медленный ответ является отдельной проблемой и не
делает сайт недоступным.

## 5. Внутренние адреса и безопасность исходящих запросов

MirvMon является доверенной административной системой и может быть установлен
в корпоративной сети для проверки внутренних ресурсов. Поэтому localhost,
частные и link-local IP-диапазоны и внутренние DNS-имена разрешены. Создание и
изменение проверок доступно только администраторам и фиксируется в append-only
audit log. Website checker не является SSRF/tenant-isolation boundary: любой
адрес, достижимый из контейнера `app` по HTTP(S), считается допустимой целью
доверенного администратора.

Ограничения исходящего запроса:

- разрешены только схемы `http` и `https`;
- credential внутри URL запрещены;
- максимальные redirect, deadline и размер тела обязательны;
- сетевые и parser-ошибки не раскрывают секреты;
- browser mutations защищены CSRF.

### 5.1. Аутентификация и дополнительные заголовки

Endpoint опционально поддерживает Basic Auth, Bearer token и дополнительные
заголовки. Имя должно быть корректным HTTP field-name и пройти серверную
политику разрешённых имён и префиксов; эта политика хранится в коде и применяется
одинаково в форме и worker. Значения credential и заголовков шифруются
существующим `APP_KEY`, никогда не возвращаются в UI после сохранения и не
попадают в логи, аудит, уведомления и диагностические сообщения.

Разрешаются обычные negotiation/client headers и пользовательские заголовки с
префиксом `X-`; отдельными разрешёнными именами предусмотрены `Api-Key` и
`Idempotency-Key`. Опасные transport/hop-by-hop заголовки, включая `Host`,
`Cookie`, `Content-Length`, `Connection`, `Transfer-Encoding`, `Forwarded`, все
`Proxy-*` и `Sec-*`, запрещены. `Authorization` задаётся только через Basic или
Bearer поля, а не как произвольный заголовок. Credential и чувствительные
дополнительные заголовки автоматически передаются по redirect только в пределах
того же origin. При переходе на другой host они удаляются, если этот destination
заранее явно не разрешён администратором.

### 5.2. Self-signed TLS

Для каждого endpoint доступна выключенная по умолчанию галочка
«Разрешить self-signed сертификат». Она отключает только ошибки доверия к
цепочке или неизвестному CA для настроенного hostname.

Даже при включённой опции обязательны:

- совпадение hostname с SAN сертификата;
- действующий период `not_before`/`not_after`;
- успешный TLS handshake и допустимый протокол.

Опция не переносится автоматически на другой hostname в redirect-цепочке.
Срок сертификата продолжает контролироваться. Замена сертификата принимается
автоматически, если hostname и срок корректны; pinning и загрузка собственного
CA в этот дизайн не входят.

В UI рядом с этой опцией явно указывается, что Basic/Bearer credential и
дополнительные заголовки могут быть перехвачены, поскольку доверие к цепочке не
проверяется. Изменение опции доступно только администратору и аудируется.

## 6. TLS-сертификаты и регистрационные домены

### 6.1. Сертификаты

TLS контролируется опционально, ежедневно и по ручному запросу. Для каждого
явного HTTPS endpoint проверяется его hostname. Все HTTPS-узлы redirect-цепочки
валидируются во время запроса; срок сертификата конечного redirect-hostname
также контролируется, если он отличается.

Инцидент всегда называет конкретный hostname. Текущее состояние сертификата
содержит subject, issuer, SAN, fingerprint, `not_before`, `not_after` и время
проверки. Смена корректного сертификата создаёт событие, но не инцидент.

Порог истечения по умолчанию: warning за 21 день, critical за 7 дней. Значения
настраиваются глобально и могут быть переопределены для сайта. Истёкший или ещё
не вступивший в силу сертификат — critical.

### 6.2. Регистрация домена

Контроль срока регистрации включается опционально для одного явно указанного
основного регистрационного домена сайта. Поле регистрационного домена можно не
заполнять, пока контроль выключен; при включении оно обязательно. Поле принимает
домен без схемы, пути и поддомена и нормализует IDN в ASCII/Punycode. Внешний
домен, на который ведёт redirect, не становится регистрационным доменом
автоматически.

Источник данных выбирается так:

1. RDAP endpoint зоны из versioned snapshot IANA bootstrap;
2. ограниченный WHOIS fallback с parser-профилем для зон без рабочего RDAP.

Обязательная зависимость от стороннего агрегатора отсутствует. Bundled snapshot
IANA и Public Suffix List можно безопасно обновлять; при ошибке обновления
используется последняя встроенная версия. Ответ кэшируется на сутки, ошибки
источника повторяются с backoff и с учётом rate limit.

Сохраняются дата истечения, registrar при наличии, источник, `checked_at` и
безопасная категория результата. Полные RDAP/WHOIS ответы не сохраняются.
Внутренние зоны, `.local` и неподдерживаемые зоны получают состояние
«Не поддерживается» без инцидента. Временная недоступность RDAP/WHOIS является
диагностикой и не влияет на доступность сайта.

Порог истечения регистрации по умолчанию: warning за 30 дней, critical за
7 дней. Значения настраиваются глобально и на уровне сайта; истёкшая регистрация
является critical.

## 7. Состояние, подтверждение и инциденты

### 7.1. Агрегированное состояние сайта

Состояние определяется по худшей активной проблеме с сохранением её типа:

- основной endpoint не отвечает — «Недоступен»;
- основной endpoint отвечает с неверным кодом или содержимым — «Проблема»;
- неисправен дополнительный endpoint — «С проблемами», но не «Недоступен»;
- превышен порог времени — «Медленно»;
- проблема сертификата или домена — warning/critical, но не «Недоступен»;
- проверки ещё не запускались — «Нет данных»;
- мониторинг остановлен — «Приостановлен».

### 7.2. Подтверждение переходов

Для открытия инцидента нужны три последовательных неуспешных проверки. Для
закрытия — две последовательных успешных. После первой ошибки до подтверждения
UI показывает «Возможная проблема 1/3», не создавая инцидент.

Время начала подтверждённого инцидента равно времени первой ошибки в серии, а
время восстановления — времени первого успеха в серии восстановления. Изменение
конкретного типа ошибки во время непрерывного outage обновляет диагностику
существующего инцидента, а не создаёт новый outage.

Независимые проблемы могут иметь одновременные инциденты, например
недоступность, медленный ответ и истекающий сертификат. Ручные проверки участвуют
в серии подтверждения, но один ручной успех не может единолично закрыть
инцидент.

Приостановка сайта прекращает планирование проверок и закрывает активные
инциденты причиной `monitoring_paused`, сохраняя историю. После возобновления
сайт начинает с состояния «Нет данных», без искусственного события
восстановления. Maintenance window не прекращает проверки и создание
инцидентов, а только подавляет доставку уведомлений.

### 7.3. Уведомления

Используются существующие `notification_outbox`, Telegram/SMTP transport,
cooldown и maintenance rules. Получатели наследуются из общих настроек и могут
быть переопределены на сайте аналогично серверу.

Сообщение содержит сайт, endpoint, вид проверки, ожидаемое и фактическое
значение, время начала и ссылку на инцидент. URL очищается от чувствительных
данных. Заголовки, token, пароль и тело ответа никогда не включаются.

## 8. Хранение метрик

`website_check_samples` сохраняет результат, категорию ошибки, настроенный и
конечный URL, HTTP-код, число redirect, DNS/TCP/TLS/TTFB/total timing,
результаты assertions и источник пробы.

Continuous aggregates:

- hourly: число проверок, transport availability ratio, full-check success ratio
  и min/avg/max TTFB и total;
- daily: те же агрегаты за сутки.

Retention для website-данных:

- raw HTTP samples — 30 дней;
- hourly aggregates — 365 дней;
- daily aggregates — без автоматического удаления;
- переходы доступности и история инцидентов — отдельно и долгосрочно согласно
  общей политике MirvMon.

Тело ответа не сохраняется ни на одном уровне.

## 9. Пользовательский интерфейс

### 9.1. Главный dashboard

Сохраняется текущая структура и визуальный язык MirvMon. После системного
баннера и заголовка располагаются:

1. полноширинный контейнер «Серверы» со статистикой и действиями;
2. сразу под ним такой же контейнер «Сайты» со статистикой и действиями;
3. общий контейнер «Требуют внимания» с проблемами серверов и сайтов;
4. существующие поиск, фильтры, группы и карточки серверов.

Контейнер серверов приводится к тому же оформлению, что и контейнер сайтов,
чтобы обе сводки воспринимались как равноправные части инфраструктуры, а не как
карточки без общего контейнера. Главный dashboard остаётся ответом на вопрос
«что требует внимания сейчас», а не превращается в полный каталог сайтов.

В главной навигации появляется пункт «Сайты».

### 9.2. Раздел сайтов

`/sites` показывает сайты по общим группам, с поиском и фильтрами состояния.
Карточка сайта компактно показывает агрегированный статус, основной URL,
последнее время ответа, доступность, ближайший TLS/domain deadline и время
последней проверки.

Создание сайта и редактирование выполняются на отдельных страницах. Формы
позволяют управлять identity, группой, регистрационным доменом, endpoint,
expected status/content, расписанием, заголовками, authentication и self-signed
опцией.

### 9.3. Страница сайта

UX следует знакомой странице сервера с предметными отличиями. Endpoint вложены
в сайт и не получают отдельные полноформатные страницы.

- «Обзор» — что мониторится, как и почему; endpoint и их состояния; основной и
  конечный URL; expected status/content; интервалы; TLS/domain; активные
  проблемы.
- «Метрики» — выбор всего сайта, основного или дополнительного endpoint и
  периода, графики транспортной доступности, успеха assertions, TTFB и полного
  времени ответа.
- «События» — активные и исторические инциденты с фильтром по endpoint и типу.
- «Настройки» — пороги и политики конкретного сайта.

Интервалы недоступности и маркеры инцидентов на графиках кликабельны и открывают
соответствующее событие. График не перегружается низкоуровневыми DNS/TCP/TLS
сериями: они остаются в диагностике проверки.

Все основные страницы должны корректно работать на desktop и viewport 390 px.

## 10. HTTP routes и права

Основные browser routes:

- `GET /sites`;
- `GET /sites/create`, `POST /sites`;
- `GET /sites/{id}` с вкладками overview, metrics, events и settings;
- `GET /sites/{id}/edit`, `POST /sites/{id}`;
- `POST /sites/{id}/check`;
- `POST /sites/{id}/pause`, `POST /sites/{id}/resume`;
- `POST /sites/{id}/settings`;
- `POST /sites/{id}/delete`.

Отдельные read-only endpoints отдают status/metrics для динамического UI без
секретов. Просмотр сайтов доступен аутентифицированным пользователям. Все
мутации требуют роли `admin`, CSRF и audit record.

В audit log фиксируются создание, изменение, удаление, pause/resume, ручная
проверка, изменения порогов, auth/headers и self-signed режима. Значения секретов
не фиксируются. Плановые проверки не создают audit spam.

## 11. Проверка и критерии поставки

### 11.1. Unit и contract tests

Обязательные unit-тесты покрывают:

- нормализацию и validation URL/domain;
- redirect и удаление credential при cross-origin переходе;
- expected status и content checks;
- расчёт timings и агрегаций;
- автомат состояний 3 failures / 2 successes;
- TLS и ограниченный self-signed режим;
- RDAP/WHOIS parsing, rate limit и unsupported zones;
- encryption и redaction секретов;
- route access, admin middleware, CSRF и переводы ru/en;
- запрет CDN-зависимостей.

HTTP/TLS/RDAP/WHOIS тесты используют детерминированные локальные fixtures. CI не
должен зависеть от доступности внешнего интернета.

### 11.2. Integration tests

На чистой TimescaleDB проверяются:

- применение и ограничения миграций;
- hypertable, continuous aggregates и retention policies;
- lease, конкурентные worker и отсутствие двойной обработки;
- переходы состояния, независимые инциденты и notification outbox;
- pause/resume и maintenance semantics;
- шифрование и отсутствие утечек секретов;
- безопасное поведение auth/header на cross-origin redirect.

### 11.3. UI, производительность и deployment

Перед завершением обязательны:

- browser smoke desktop и 390 px для dashboard, списка, создания,
  редактирования и всех вкладок сайта без console errors;
- существующий `bin/benchmark-dashboard` на 50 и 1000 серверов, поскольку
  dashboard меняется;
- новый benchmark списка/сводки на 50 и 1000 сайтов с несколькими endpoint и
  ограниченным числом запросов к БД;
- clean запуск production Compose ровно из `app` и `db`;
- успешные `/livez`, `/readyz` и heartbeat нового worker;
- полный набор обязательных PHP, frontend, audit, shellcheck, Docker и
  integration gates из `AGENTS.md`.

Функция считается готовой только после прохождения этих проверок и обновления
README, архитектурной, технической и эксплуатационной документации на русском и
английском там, где соответствующие разделы двуязычны.

## 12. Явно исключено из текущего объёма

- проверки с выбранных агентов и distributed quorum;
- публичный или неадминистративный конструктор проверок;
- методы HTTP с побочными эффектами;
- регулярные выражения для body;
- хранение тела ответа или сырых RDAP/WHOIS ответов;
- TLS certificate pinning и пользовательское CA-хранилище;
- обязательный внешний сервис агрегации domain data;
- выделенный третий production-контейнер для checker.
